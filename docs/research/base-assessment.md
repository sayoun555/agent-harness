# 베이스 평가: 이전 하네스는 좋은 출발점이었나

질문: agent-harness 는 이전 프로젝트의 하네스에서 출발했다. 베이스가 나쁘면 위에 무엇을 쌓아도 나쁘다. 그 베이스는 좋았나.

답: **생각의 베이스로는 좋았고, 증거의 베이스로는 약했고, 코드의 베이스로는 약했다.** agent-harness 는 생각만 물려받고 코드는 다시 썼다. 그래서 물려받은 약점은 증거 쪽 하나다.

## 무엇이 좋았나

- **문제 정의가 정확했다.** "산문 규칙은 바람이고 하네스는 강제다." 업계가 2026년 2월에 이름 붙인 것과 같은 생각을 그 전에 코드로 옮겼다.
- **자기 측정이 있었다.** 16개 실험, 부정 결과도 그대로 기록. Marmelab 조사에서 하네스의 60%는 테스트도 eval 도 없다.
- **정직했다.** 스스로 과장을 교정하고, 외부 하네스를 비판한 기준을 자기에게도 들이댔다.
- **deny 규칙이 있었다.** 391개 저장소 중 12개만 한다.
- **트러블슈팅 기록이 있었다.** 한국어 마커 오탐 교훈은 agent-harness 에서 그대로 재발했고, 그 기록 덕분에 바로 고쳤다.

## 무엇이 약했나

**증거**
- 핵심 결론 "주입은 0, 검증은 양수" 가 n=1~8, 천장 효과, 자기 채점, 일부 재현 불가 위에 서 있다. 방향일 뿐 증명이 아니다 ([pilot-evidence.md](pilot-evidence.md)).

**코드**
- 스크립트에 자동 테스트가 없었다. 합성 입력을 손으로 파이프해 확인했다.
- 만들어 두고 실제로 돌려 보지 않은 부품이 있었다(대량 배치 감독자 워크플로우).
- 측정상 값이 가장 컸던 런타임 검증 렌즈는 기본값이 꺼져 있었다.
- 측정상 값이 거의 없던 주입 기계(설계 문서 라우팅, 발췌 검색)는 그대로 유지하고 있었다.
- 문서와 실제가 어긋난 곳이 있었다. 문서는 브랜치 보호가 켜져 있다고 했지만, 경량판 저장소에서는 꺼져 있었다.
- 자기 검증으로 fail-open 버그 2건이 나중에 발견됐다.

## agent-harness 는 무엇을 물려받았나

| 물려받음 | 버림 | 새로 만듦 |
|---|---|---|
| 강제 > 산문이라는 원칙 | 설계 문서 주입·라우팅 | 기능 원장과 상태 전이 |
| 결정론 게이트, 약한 마커는 경고 | 다수결 패널 | 제한 루프 그래프, 사람 노드 |
| 적대자 프로토콜(과설계도 위반) | 스택 전용 규칙을 코어에 박는 것 | 테스트 약화 결정론 검사 |
| footgun 을 설정 데이터로 두는 구조 | 수동 검증 | 통과 못 한 변경 보관 |
| 제한 반복 + 게이트 속이기 감시 | | 자동 테스트 45개 + 그래프 시뮬레이션 + CI |

코드는 다시 쓰면서 테스트를 붙였다. 그런데 다시 쓴 쪽에도 테스트 실행기 버그가 있어서, 한동안 중간 단언이 무시되고 있었다. 테스트가 있다는 것만으로는 충분하지 않고, 테스트가 실제로 실패를 잡는지도 확인해야 한다.

## 그래서 베이스가 좋은지 어떻게 확정하나

베이스를 한 번 더 다시 쓰는 것이 답이 아니다. **베이스가 걸고 있는 내기를 독립적으로 재는 것**이 답이다. 내기는 이것이다: "외부 검증으로 구속한 루프가, 구속하지 않은 에이전트보다 결과가 낫다."

| 항목 | 이전 파일럿 | 필요한 것 |
|---|---|---|
| 과제 | 직접 만든 fixture | 공개 벤치마크 일부(SWE-bench Verified, Terminal-Bench) 또는 실제 프로젝트 기능 |
| 표본 | 1~8 | 과제 20개 이상 |
| 비교 | 하네스 있음 vs 약간 다른 하네스 | Claude Code 그대로 vs agent-harness 루프 |
| 채점 | 같은 에이전트 계열 | 숨겨 둔 테스트(에이전트가 못 보는 것) |
| 기록 | 일부 유실 | 원시 결과 전부 커밋 |
| 비용 | 안 잼 | 토큰과 시간 |

차이가 없으면 루프를 줄인다. 검증 노드를 끈 버전도 같이 돌려서, 적대자가 비용만 드는지도 본다.
