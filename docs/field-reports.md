# 현장 보고와 반영

실제 프로젝트에 하네스를 붙여 쓰면서 나온 문제와, 하네스가 어떻게 바뀌었는지 정리한다.
보고는 다섯 번(A~E) 나왔다. 개발 중에 하네스 스스로 찾은 버그도 마지막에 함께 적는다.

| 보고 | 적용 환경 |
|---|---|
| A~D | Android(Kotlin) 신규 저장소. 커밋 0개, "커밋 흔적 금지 · 하네스 파일을 git 에 넣지 않음 · 루프는 쓰지 않음" |
| E | C 펌웨어 저장소. 로컬 전용 설치 · 커밋 없이 운용 · 순차 루프. 세션은 다른 저장소에서 열었다(그 세션에는 플러그인이 없고, 워크플로우는 인라인 사본으로 돌렸다) |

## 보고 A — 커밋 없는 운용과 품질 기준 (10건)

| # | 문제 | 반영 |
|---|---|---|
| A1 | 기능당 구현·검증 서브에이전트 구조가 루프 안에만 있었다. 루프는 커밋을 3곳에서 만들어서, 커밋을 빼려고 루프를 끄면 메인이 구현과 자기 검증을 혼자 했다 | `loop.autoCommit: false`(커밋 없는 운용). 기록은 원장과 기준선에, 보관은 패치로. 스킬 2B "루프 없이도 기능마다 다른 서브에이전트" |
| A2 | init 이 추적 대상 파일(.gitignore · .claude/settings.json · docs/design)을 건드렸다 | `init --local`: 무시 목록은 .git/info/exclude, 플러그인은 settings.local.json, 설계 문서는 .harness/design |
| A3 | 독립 검증의 반려가 원장에 들어가지 않아 매번 손으로 reject 했다 | verified(게이트) → reviewed(독립 검증) → passing(기록) 상태 분리, `feature review` |
| A4 | 커밋 0개 저장소에서 diff · test-guard 가 비었다 | 기준선(`baseline save`, git 트리 객체). 모든 비교를 "기준 트리 대 현재 트리" 로 통일, untracked 포함 |
| A5 | generic 프리셋에 코드 기준이 없어 구조 문제(플래그 상태 기계, 섞인 동시성, 600줄 파일)가 전부 통과했다 | 공통 코드 기준 Q1~Q7 을 프리셋과 상관없이 항상. Android 프리셋과 A1~A6 |
| A6 | 크기 초과가 경고로만 끝났다 | `rules.sizePolicy: block-growth`(새로 커진 파일만 차단), 검증 컨텍스트에 게이트 경고 |
| A7 | stub 패턴이 Kotlin `TODO()` 같은 언어별 stub 을 놓쳤다 | 언어별 stub 패턴(Kotlin · Python · Rust · Java) |
| A8 | 같은 트리 병렬에서 빌드가 충돌해 손으로 조율했다 | 같은 트리 병렬: 기능별 범위(`feature claim`) + 빌드 잠금(`lock run`) |
| A9 | 전역 디스패처와 플러그인 훅이 두 번 돌았다 | 저장소 밖(사용자 전역 설정)의 디스패처를 고쳐 `.harness/project.json` 과 settings.local.json 도 본다 |
| A10 | 사람 결정이 설계 문서 표에만 있어 프롬프트마다 손으로 복사했다 | `design import` 가 "사람 결정" 행을 기능의 decisions 로 옮긴다 |

## 보고 B — 검증의 기준과 프롬프트 (5건)

| # | 문제 | 반영 |
|---|---|---|
| B11 | 검증 프롬프트가 "의미 위반만, 확신 없으면 통과" 라서 구조 문제를 보지 않았다 | 반려 기준 셋(REQ 요구 위반 · REG 회귀 · 기준 ID). 검증자는 승인·반려 대신 항목마다 kept · violated · na 대조표를 내고, 하네스가 판정한다 |
| B12 | 프로젝트가 쌓은 품질 기준을 넣을 자리가 없었다 | `.harness/criteria/` 와 `criteria add`. 구현 프롬프트와 대조표에 자동으로 들어간다 |
| B13 | 설계가 1차 요구 문서 없이 파생 문서만으로 됐다 | 설계 양식 "요구 원천" 절(1차 문서 필수), "요구 추적" 표, `design trace` |
| B14 | 루프 밖에서 메인이 서브에이전트 프롬프트를 손으로 써서 품질이 흔들렸다 | 표준 프롬프트 `prompt implement|review ID`. 서브에이전트에게는 그 명령을 실행하라는 한 줄만 준다. 요구를 많이 맡은 기능은 설계 검사가 경고 |
| B15 | 서브에이전트 시작 비용이 컸다(다른 저장소의 CLAUDE.md, 켜진 플러그인·MCP) | README 운용 가이드. 하네스 전용 에이전트 정의(아래 측정) |

## 보고 C — 루프 밖 운용 (6건)

| # | 문제 | 반영 |
|---|---|---|
| C1 | 같은 구현 에이전트에 후속 지시를 이어 붙여 25만 토큰을 넘었고, 검증자도 재사용했다 | 프롬프트 머리에 "기능 · 시도 N · 구현|검증 전용". 스킬에 "시도마다 새 구현자, 검증마다 새 검증자". Agent 도구의 재사용 자체는 하네스가 막을 수 없다 |
| C2 | 검증 통과 뒤에 고친 파일이 다시 검증되지 않았다 | drift: 기록할 때 파일 내용 해시를 남기고, 바뀌면 루프 시작·audit 때 다시 연다. 뒤 기능이 검증을 거쳐 고친 것은 흡수한다 |
| C3 | 작업 중 기준이 바뀐 것을 진행 중 에이전트가 몰랐다 | 구현 시점의 기준 버전(내용 해시)을 남기고, 검증 때 다르면 경고와 새 항목 목록 |
| C4 | 테스트·검증을 통과했는데 실행하니 렌더링 결함이 나왔다 | 실행 렌즈(`harness run`): 설치·실행·스크린샷·로그를 검증자에게. 기본 꺼짐, android·nextjs 프리셋에 예시 |
| C5 | 이전 세션의 UX 레퍼런스 지시가 사라졌다 | 설계 양식 "UX·레퍼런스" 절. 지정이 없으면 "없음", 비워 두면 검사가 막는다 |
| C6 | 검증자가 특정 상태만 막는 분기를 수정안으로 냈다 | 검증 프로토콜: 수정안은 구조로, 제안도 기준(Q1)에 스스로 대조 |

## 보고 D — 커밋 없는 운용의 기록·보관 (5건)

| # | 문제 | 원인 | 반영 |
|---|---|---|---|
| D1 | 범위 없는 기능 A 의 위험 판정이 B 의 변경까지 A 의 패치로 보관하고 트리에서 지웠다 | 범위가 없으면 트리 전체를 그 기능의 것으로 봤다 | 소유권 확인: 범위 없는 기능은 같은 트리에 기록 전인 다른 기능(검증·검토 통과, 또는 이 트리에서 구현 시작)이 있으면 verify · review · record · approve 가 아무것도 건드리지 않고 멈춘다 |
| D2 | 보관 직후 B 가 빈 트리로 passing 이 됐다 | 기록이 "검토 통과" 만 보고 변경이 그대로인지 보지 않았다 | 게이트·검토 때 변경 해시를 남기고, 다음 단계에서 다르면 되돌린다. 기록할 변경이 비면 되돌린다 |
| D3 | diff 가 maxDiffLines 를 넘으면 검증 프롬프트가 비었다 | `git diff | head` 에서 SIGPIPE + pipefail | diff 를 파일에 쓰고 자른다. 잘렸으면 "N줄 중 M줄" 안내. check 의 같은 패턴은 `grep -m` 으로 |
| D4 | .harness 가 gitignore 된 저장소에서 ignore 경고가 반복됐다 | git add 의 pathspec 에 ignore 경로가 이름으로 들어갔다 | 전체를 담은 뒤 .harness 를 인덱스에서 뺀다 |
| D5 | 커밋 없는 저장소에서 `check` 가 아무 파일도 검사하지 않고 통과했다 | staged · 추적 파일만 봤다 | 인자 없으면 기준 대비 바뀐 파일, `--all` 은 untracked 포함, pre-commit 훅은 `--staged` |

## 보고 E — 진행 중인 기능과 루프의 반복 (9건)

| # | 문제 | 원인 | 반영 |
|---|---|---|---|
| E1 | 기록 전인 기능 A 의 변경이 통과한 기능 B 를 drift 로 다시 열고, A 와 B 가 소유권 확인에서 서로를 막았다(통과 기능 6개가 한꺼번에) | drift 가 진행 중인 기능을 보지 않았다. 다시 열 때 · 기록할 때 진행 중 표시(`implementedUnder`)를 지우지 않았다 | "진행 중" 판정을 한곳(`JQ_IN_FLIGHT`)에 두고 소유권과 drift 가 같이 쓴다. 진행 중 기능이 맡은 파일은 drift 에서 빼고, 범위 없는 진행 중 기능이 있으면 미룬다. 기록 · drift 재오픈 · reset 이 진행 중 표시를 지운다 |
| E2 | reviewed 기능이 소유권 확인에 막히면 정식 명령으로 빠져나올 수 없어 원장을 손으로 고쳤다 | claim 은 pending, reset 은 막힘 · 승인 대기 · 판단 대기에서만 됐다 | claim 을 verified · reviewed 에서도(범위가 바뀌면 게이트부터 다시). reset 을 통과 전 모든 상태에서(작업 트리는 건드리지 않고 진행 중에서 뺀다) |
| E3 | 순차 모드에서 범위가 잡히지 않아, 검토 뒤 트리가 바뀌면 승인한 작업이 다시 열렸다 | 같은 트리 병렬만 구현자가 바꾼 파일을 claim 했다 | 커밋 없이 운용하면 순차에서도 claim. 다시 claim 하면 범위에 더한다 |
| E4 | 게이트가 거부(exit 2)되면 루프가 같은 기능을 18바퀴 돌았다. 잃은 review 응답 때문에 승인된 기능이 기록되지 않았다 | 거부는 stderr 에만 남아 루프에는 "응답 없음" 이었고, 원장이 실패를 세지 않아 한도에 걸리지 않았다 | `--json` 이면 거부도 stdout 에 error 한 줄. 응답이 없거나 거부면 원장을 다시 읽어 이어 간다. 원장이 세지 않는 같은 결과가 두 번 연속이면 `stuck` 으로 멈춘다 |
| E5 | 다른 저장소에서 연 세션에서 전용 에이전트를 못 찾았고, 상대 경로 명령이 깨졌다 | CLI 는 프로젝트 설정만 보고 이름을 준다. 명령은 작업 디렉터리가 프로젝트라고 가정했다 | 전용 정의를 띄우지 못하면 기본 에이전트로 바꿔 계속한다. `args.projectRoot`(`harness path project`)를 받으면 그 루트에서 실행한다. 워크플로우 사본이 작업 디렉터리 밖이면 Workflow 도구가 거부하는 것은 그대로 — 스킬이 2B 로 안내한다 |
| E6 | 다음 기능을 고르는 명령의 응답을 잃었는데 루프가 "완료" 로 끝냈다 | 선택 결과가 없으면 응답 유무를 가리지 않고 all-done 으로 봤다 | 빈 결과(`{}` · `[]`)만 완료. 응답이 없거나 거부면 `ledger-unreadable` 로 멈춘다 |
| E7 | 다시 연 기능을 재검증해 승인받아도 "기록할 변경이 없다" 로 기록을 거부했다 | 그 기능의 코드는 이미 기준에 들어 있어 diff 가 비었다. 빈 변경 거부(D2)는 처음 기록하는 기능을 위한 것이었다 | 한 번 기록된 기능(`verifiedFiles` 가 있다)은 변경 없이 다시 검증한 것도 기록한다. 앞서 검증한 파일을 지금 내용으로 다시 남긴다. 다시 구현한 변경이 휩쓸린 경우는 검토 때 해시가 달라져 그대로 걸린다 |
| E8 | 검증자가 판정을 직접 제출했는데 루프가 한 번 더 제출해 오류가 났다 | 검증 프롬프트가 "루프 밖에서 혼자 실행할 때는 제출" 이라고만 했다 — 검증자는 자기가 루프 안인지 모른다 | 부르는 쪽이 정한다: `prompt review ID --mode loop` 면 반환만 하고 제출하지 않는다(기본 standalone 은 스스로 제출). 루프는 loop 로 부른다 |
| E9 | `feature list --json`(원장 전체) 출력이 반복해서 걸러져 루프가 멈췄다 | 루프는 상태만 필요한데 실패 출력 · 대조표가 실린 원장 전체를 읽었다 | `list` · `next --json` 에 `--fields`, 기능 하나만 읽는 `feature show ID`. 루프는 선택에 id · attempts · figma, 상태 확인에 그 기능의 status, 끝 요약에 id · status · lastFailure · question 만 읽는다. 모든 기능을 읽는 것은 끝 요약뿐이다. 구현자 · 검증자가 받는 내용은 루프를 거치지 않고 `prompt` 가 원장 전체에서 만들므로 줄지 않는다 |

## 하네스 스스로 찾은 것

| 문제 | 반영 |
|---|---|
| 테스트 러너가 단언 실패를 무시했다(set -e 가 함수 안에서 꺼짐) | 실패를 플래그로 기록 |
| 한글 절 제목 비교가 로케일에 따라 모두 "같다" 로 나왔다(awk `==`) | 바이트 비교 |
| BSD grep 과 ugrep 의 정규식 차이 | 단순한 ERE 로 |
| 커밋 운용에서 원장 파일이 "삭제됨" 으로 보였다(HEAD 트리에는 있고 현재 트리에는 없음) | 모든 트리 비교를 한 함수로 모으고 .harness 를 양쪽에서 뺀다 |
| 커밋 운용에서 기록 뒤 원장이 더러워졌다(해시를 커밋 뒤에 씀) | 통과 표시와 해시를 커밋 전에 함께 쓰고, 실패하면 원장을 통째로 되돌린다 |
| audit 가 검증 후 변경을 다시 열고도 "회귀 없음" 으로 성공했다 | 다시 연 기능도 audit 실패로 보고 |
| 단독 `review` 가 인자 없으면 staged 파일만 봤다(D5 와 같은 문제) | 기준 대비 바뀐 파일 |
| 설계 표의 가운데 칸이 비면 뒤 칸이 앞으로 밀렸다(bash read 가 연속 탭을 합침). 판·날짜가 빈 요구 원천이 "종류가 틀렸다" 로 나왔다 | 줄 단위로 읽는 곳은 공백이 아닌 구분자(0x1F)로 |
| 검증자가 대조표 파일을 작업 트리에 저장하면 D2 의 해시 확인에 걸린다 | 저장 위치를 `.harness/verdicts/<ID>.json` 으로 지정 |
| 루프가 하네스 명령 하나마다 띄우는 실행 에이전트도 기본 에이전트였다 | 명령 실행 전용 정의(Bash 만) |
| 같은 트리 병렬에서 두 기능이 같은 파일을 맡아도 막지 않았다. 루프가 기능마다 claim 직후 기록까지 해서, 앞 기능의 범위가 풀린 뒤 뒤 기능이 claim 했다 | claim 이 다른 기능의 범위와 겹치면 거부. 루프는 게이트 전에 바퀴 안의 범위를 모두 먼저 적는다 |
| `trace report` 를 현장 E 의 기록에 돌려 보니 기능당 시간이 첫 게이트부터라 구현 시간이 빠졌다 | 구현 시작(`implement`)을 trace 에 남기고, 거기서 처음 passing 까지 잰다 |
| 같은 보고서에서 통과한 기능의 시도 수가 모두 0 으로 나왔다(원장의 시도 수를 읽음) | 처음 통과 전까지의 게이트 실패 · 검토 반려를 trace 에서 센다 |
| 같은 보고서가 REQ · REG 반려를 "기능을 넘어 반복된 기준" 으로 셌다 | 요구 · 회귀는 기능마다 내용이 달라 반복이 아니다. 품질 기준 ID(Q2 · P1 …)만 센다 |
| 테스트가 없는 단언 함수(`assert_not_contains`)를 불렀는데 "command not found" 만 찍고 통과했다 | 도우미를 추가했다. 러너가 없는 명령을 실패로 보게 하지는 않았다 |

## 원장 퍼즈가 찾은 것

보고를 기다리지 않고 규칙끼리 부딪히는 곳을 찾으려고 `tests/fuzz-ledger.mjs` 를 만들었다. 실제 하네스 명령을 무작위 순서로 돌리고(구현 · 손 수정은 파일 쓰기로 흉내, 모델 호출 없음), 매 단계 비정상 종료 · 보관 밖 파일 변경 · 남의 변경을 치우는 보관 · 기록 직후 drift 를, 끝에 루프와 문서의 복구만으로 모든 기능이 끝 상태에 닿는지를 본다. 처음 몇 차례(한 번에 시드 30~60개 × 두 운용) 돌리는 동안 아래 다섯이 나왔다. 고친 뒤 처음 시드 60개(120개 순서 × 25단계)와 다른 시드 200개(400개 순서 × 30단계)에서 위반이 없다. 각 항목은 run.sh 에 재현 테스트로 고정했다(고치기 전 코드에서 실패하는 것을 확인).

| 문제 | 원인 | 반영 |
|---|---|---|
| 범위 없는 기능의 판단 요청(`ask`)이 같은 트리의 다른 기능 변경까지 자기 보관본으로 치웠다(60개 순서 중 15개) | 변경을 보관하는 명령 중 `ask` 만 소유권 확인이 없었다(D1 과 같은 종류) | `ask` 도 소유권을 먼저 본다. 루프는 범위를 판단 요청보다 먼저 적는다 |
| 커밋 운용에서 범위를 잡은 기능의 보관 · 기록이 다른 기능의 변경까지 담았다 | claim 은 받았지만 커밋(`git add -A`)과 보관(브랜치)은 트리 전체를 담았다 | 커밋 운용에서는 claim 을 거부한다(adopt 가 커밋 없는 운용에서 거부되는 것과 짝). 안내문도 운용 방식에 맞는 길(reset)을 준다 |
| 보관된 기능이 범위를 쥔 채로 남아, 그 파일을 고쳐야 하는 다른 기능들의 claim 이 계속 거부되고 서로 막혔다 | 보관할 때 진행 중 표시만 지우고 범위는 두었다 | 보관하면 범위도 푼다. 승인하면 보관본의 경로로 다시 잡는다 |
| 커밋 운용에서 기능 하나가 막히면 다음 사전 점검이 "트리가 깨끗하지 않다" 로 실패했다 — 다음 루프가 시작하지 못한다 | 기록되지 않고 떠난 기능은 원장만 바꿔 두는데, 사전 점검은 원장까지 봤다 | 원장을 빼고 본다(approve 의 확인과 같은 기준) |
| 커밋 운용에서 끊긴 실행이 남긴 진행 중 표시가 서로를 막고, verified · reviewed 는 루프가 고르지 않아 남았다 | 트리가 깨끗해도 진행 중 표시를 그대로 믿었다 | 사전 점검이 통과하면(트리가 깨끗하면) 남은 진행 중 표시를 푼다. verified · reviewed 는 pending 으로 |

## Windows 지원에서 찾은 것

CI 에 Windows(Git Bash) 실행기를 붙이자 테스트 181개 중 109개가 실패했다. 하네스 본체의 원인은 셋, 나머지는 테스트 쪽 경로 표기였다. Windows 용 하네스를 따로 만들지 않고, OS 차이를 `lib/platform.sh` 한곳에서 흡수한다.

| 문제 | 원인 | 반영 |
|---|---|---|
| 상태 · 경로 비교가 거의 모두 어긋났다(`애드온이 없다: supabase` 뒤에 줄바꿈) | 네이티브 `jq.exe` 는 줄 끝을 CRLF 로 낸다. `$(jq -r …)` 값 끝에 `\r` 이 붙었다 | Windows 에서만 `jq --binary`(LF 그대로). 판정은 `$OSTYPE` 으로 — 프로세스를 띄우지 않는다 |
| 원장 명령이 `필요한 명령이 없다: shasum` 으로 멈췄다 | Git Bash 에는 perl 의 `shasum` 이 없고 `sha1sum` 만 있다 | 있는 쪽을 고른다(`SHA1_COMMAND`). 출력이 같아 이미 적힌 해시(기준 버전 · 실패 지문)가 그대로 맞는다 |
| (예방, 실측 아님) 훅이 편집 파일을 프로젝트 기준 경로로 바꾸지 못할 수 있다 | Windows 프로그램은 경로를 `C:\Users\…` 로 넘긴다(Claude Code 훅 입력의 실제 형식은 확인하지 않았다). `dirname` · `cd` 는 `/` 만 구분자로 본다 | 경로 정규화(`canonical_path`)가 Windows 에서 `\` 를 `/` 로 바꾼다 |
| 테스트가 하네스와 다른 루트 표기(`/c/…` 대 `C:/…`)로 비교했다. 외부 도구를 숨기려고 줄인 PATH 에서 jq 까지 사라졌다 | git 은 `C:/…`, `$PWD` 는 `/c/…` 로 낸다. Windows 의 jq 는 `/usr/bin` 밖에 있다 | 테스트도 루트를 git 최상위로 구한다(`project_root`). 줄인 PATH 에는 jq 만 남긴다(`path_without_extras`) |
| 시뮬레이션이 bash 에 경로를 넘기지 못했다 | Node 의 `D:\a\…` 를 bash 가 역슬래시 이스케이프로 먹었다. PATH 구분자(`;`), `import()` 의 절대 경로(URL 이 아님), 경로를 넣은 정규식도 같은 종류 | `bashPath`(`/` 표기) 한 도우미, `path.delimiter`, `pathToFileURL`, 정규식 대신 문자열 포함 |
| Windows CI 가 3시간 걸렸다(테스트 50분 · 퍼즈 2시간, macOS 는 합쳐 15분) | 하네스는 명령마다 jq · git 프로세스를 많이 띄우고, Windows 는 프로세스 하나가 열 배쯤 비싸다 | 퍼즈가 보는 원장 규칙은 OS 와 무관하므로 Windows 에서는 작게(6시드). CI 는 앞 단계가 실패해도 나머지 테스트를 돌려 한 번에 다 본다 |

남은 한계: 실제 Windows 의 Claude Code 에서 설치 · 훅 · 루프를 돌려 보지는 않았다. 명령 하나가 macOS 보다 열 배쯤 느리다.

## 그 뒤 추가

| 요청 | 반영 |
|---|---|
| 루프에서 겪은 문제와 해결을 문서로 남겨야 한다(지금까지는 현장 세션이 손으로 적어 보냈다) | `trace report`: trace 와 원장에서 `.harness/runs/report.md` 를 만든다. 문장은 검증자 · 하네스가 trace 에 남긴 사유 그대로 엮어 모델을 부르지 않는다. 구현 시작(`implement`) · 게이트 실패 내용 · 루프 종료 이유(`loop-end`)를 trace 에 더 남긴다. 루프는 끝날 때 만든다. 보고서는 이미 무시되는 `.harness/runs/` 에 둔다 — 무시되지 않는 곳에 쓰면 커밋 운용의 사전 점검이 더러운 트리로 실패한다. 기능을 넘어 반복된 품질 기준을 세어, 교훈 파일(하네스²의 EXPERIENCE.md 같은 것)이 필요한 프로젝트인지 데이터로 본다 — 현장 E 에서는 반복이 없었다(반려 7건 중 품질 기준은 Q2 · Q3 · P1 각 1건) |
| 루프가 돌 때 토큰이 얼마나 남았는지 실시간으로 보고 싶다 | 워크플로우가 아는 것은 이 실행의 출력 토큰뿐이고 요금제 한도는 모른다. 헤드리스 `claude -p /usage` 가 모델을 부르지 않고(토큰 0, 약 3초) 세션 · 주간 사용량을 준다는 것을 확인해 `harness usage` 로 감쌌다. 루프는 바퀴마다 읽어 진행 줄에 붙이고(`[3/10] F-04: review → reject · 사용량 세션 34% · 주간(전체) 18%`), 기준(기본 90%)을 넘으면 다음 기능을 시작하지 않는다 — 한도에 걸려 구현 중간에 끊기면 반쯤 바뀐 트리가 남는다. 멈춘 이유는 보고서의 이상 신호에 남는다. 비용은 바퀴마다 명령 실행 에이전트 한 번. `--bare` 로 부르면 구독 사용량이 나오지 않아 쓰지 않는다. 응답 형식(영문 줄)이 바뀌거나 구독이 아니면 읽지 못한 것으로 보고 멈추지 않는다 |
| 루프가 매번 명령 권한 확인에서 멈춘다 | `init` 은 플러그인만 켜고 허용 규칙을 넣지 않아, 바퀴마다 부르는 `.harness/bin/harness …` 부터 사람에게 물었다. `harness permissions` 와 `init` 이 하네스 자신 · `build.compileCommand` · `testCommand` 를 `.claude/settings.local.json` 에 넣는다(`&&` · `;` · `|` 로 이은 명령은 나눠서, `cd` 와 치환이 든 명령은 빼고). 처음에는 원장의 acceptance 도 넣고 루프 사전 점검마다 갱신하려 했으나, 작업 중 자동 모드 분류기가 "에이전트의 권한 자기 수정" 으로 막았고 지적이 맞았다 — acceptance 는 에이전트가 `feature add` 로 쓸 수 있어서 에이전트가 제 권한을 넓히는 길이 된다. 그래서 사람이 정한 값만, 사람이 실행할 때만 넣는다. 파일은 커밋하지 않는다(`.git/info/exclude` — 공유 설치에서 트리가 더러워지면 사전 점검이 실패한다). 커밋된 settings.local.json 은 건드리지 않는다. 에이전트가 그때그때 치는 명령은 규칙으로 알 수 없어 자동 모드로 돌리라고 안내한다 |
| 포맷을 아무도 보지 않는다(현장 세션의 지적) | 확인해 보니 맞았다. 어느 프리셋에도 포매터 검사가 없고 경고도 없었다. 검증자는 대조표의 기준 항목만 판정하는데 포맷 항목이 없다. ("검증자 지시문이 포맷은 반려하지 않는다고 정했다" 는 부분은 하네스에 없는 문장이었다 — 결과는 같다.) `build.formatCheckCommand` 를 verify 의 컴파일 다음 게이트로, `formatCommand` 를 구현 프롬프트의 마무리 지시로 넣었다 — 구현자가 미리 맞춰 포맷 때문에 다시 도는 바퀴가 없게. 프리셋 기본값은 비운다: Spotless 가 없는 Spring 프로젝트에 넣으면 모든 기능이 막힌다. 대신 `init` 이 빌드 파일에 설정된 Spotless · ktlint · Prettier 를 찾아 채우고, 없으면 경고하고, 설정이 이미 있으면 넣을 줄만 알린다. 포매터는 프로젝트 전체를 보므로 기존 코드가 포맷돼 있지 않으면 모든 기능이 남의 코드로 막힌다 — 루프 사전 점검이 먼저 돌려 보고 실패하면 시작하지 않는다(한 번 포매팅해 반영하면 그 뒤로는 기능이 바꾼 파일만 걸린다). 같은 트리 병렬 구현에서는 포매터가 다른 기능의 파일까지 바꾸니 구현자에게 돌리지 말라고 한다. 이때 다른 기능의 작성 중 파일로 게이트가 실패할 수 있는 것은 컴파일 게이트와 같은 성질이다 |
| Figma 를 주면 그 화면대로 만들어야 한다. 구현자는 Figma MCP 를 보고 구현하면 된다 | 기능 분해의 "화면" 칸(Figma 노드 링크) → 원장 `figma`. 구현·검증 프롬프트에 그 노드를 Figma MCP 로 열라는 지시. 열 수 없으면 구현자는 판단 요청, 검증자는 REQ 위반 |

### 보고 E 의 루프는 어디서 시간을 썼나

워크플로우 실행 4번의 에이전트 96개(기본 에이전트, 순차, 커밋 없음)를 에이전트 기록의 시각과 토큰으로 집계했다.

| 노드 | 수 | 평균 | 최대 | 출력 토큰 |
|---|---|---|---|---|
| 원장 전체 읽기 (`feature list --json`) | 12 | 134초 | 206초 | 202,523 |
| 구현 | 23 | 57초 | 169초 | 21,759 |
| 검증 | 5 | 55초 | 99초 | 8,189 |
| 판정 제출 | 5 | 15초 | 25초 | 1,867 |
| 다음 기능 선택 | 20 | 6초 | 25초 | 10,593 |
| 게이트 | 23 | 5초 | 6초 | 4,808 |

- 원장 전체 읽기가 에이전트 시간의 45%(1,604 / 3,593초), 출력 토큰의 81%였다. 원장이 약 80KB 이고, 명령 실행 에이전트가 stdout 을 원문 그대로 다시 써서 돌려주기 때문이다. trace 에서 기록 한 번이 3~6분 걸린 구간이 이것이다. 지금은 끝 요약이 2.1KB, 상태 확인이 기능 하나의 상태 약 20바이트다(E9).
- 같은 자리를 18바퀴 돈 실행이 26분이었다(E4).
- 기능 하나가 막힘 없이 돌 때 게이트 · 검증 · 기록은 2~3분이었다.
- trace 의 1~3시간대 공백(105분 · 218분)은 그 시간에 메인 세션 기록도 워크플로우도 없었다. 하네스가 돈 시간이 아니라 세션이 멈춰 있던 시간이다.
- 명령 하나마다 띄우는 실행 에이전트의 고정 비용은 5~15초다. Workflow 에는 셸이 없어서 줄일 수 없는 구조 비용이다.

## 남은 한계

- 하네스 전용 에이전트 정의는 실제 루프에서 작은 기능 하나로만 돌려 봤다. 규모 있는 기능과 병렬 모드는 시뮬레이션까지다.
- 같은 트리에서 범위 없이 프롬프트 없이 손으로 두 기능을 동시에 만들면, 게이트 전에는 하네스가 누구 변경인지 알 수 없다. 게이트 뒤에 섞이면 해시 확인이 잡는다.
- Agent 도구의 서브에이전트 재사용은 프롬프트와 스킬 규칙으로만 막는다.
- 보고 E 의 수정(E1~E9)은 테스트와 시뮬레이션으로만 확인했다. 실제 루프에서 다시 돌려 보지 않았다.
- 세션이 프로젝트 밖에서 열려 있으면 Workflow 도구가 워크플로우 사본 경로를 거부한다. Claude Code 쪽 제약이라 하네스가 풀 수 없다(스킬이 루프 없이 진행하도록 안내).
- 순차 · 병렬의 자동 범위는 구현자가 보고한 바꾼 파일(`filesChanged`)을 믿는다. 빠뜨린 파일은 범위 밖에 남아 그 기능의 기록에 들어가지 않는다.
- `stuck` 은 그 기능만 건너뛰지 않고 루프 전체를 멈춘다. 같은 원인이 다른 기능도 막는 경우가 많아서다.
- E9 에서 원장 출력의 무엇이 걸렸는지는 확인하지 못했다. 읽는 양을 줄였을 뿐이다.
- `--local` 설치의 shim 은 하네스 저장소의 작업 트리를 그대로 실행한다. 하네스를 고치는 저장소를 그대로 쓰면, 돌고 있는 루프가 수정 중인 코드로 돈다(보고 E 에서 실제로 그랬다). 현장에는 따로 받은 사본을 쓴다.
