# 설계 기준 — 공통 (초안)

> 초안이다. 프로젝트 소유자가 우선순위와 적용 조건을 고쳐 확정한다.
> 기준은 무차별로 적용하지 않는다. 각 기준의 "적용 조건" 에 해당할 때만 쓴다. 이전 파일럿에서 기준을 단순 과제에 일괄 적용하자 과설계가 나왔다.

기준끼리 부딪히면 **번호가 작은 쪽이 이긴다.** 예를 들어 C3(필요한 만큼만)은 F4(디자인 시스템)보다 앞선다. 토큰이 없는 작은 프로젝트에 토큰 체계를 새로 만들지 않는다.

## C1. 완성의 정의부터

- **규칙:** 설계 전에 "완성" 이 무엇인지 적는다. 누가 쓰는가, 데이터는 어디서 오는가, 어떤 상태가 되면 끝인가.
- **이유:** 완성 정의가 없으면 루프의 종료 조건(acceptance)을 쓸 수 없고, 범위가 계속 늘어난다.
- **적용 조건:** 항상.
- **확인 방법:** 설계 문서의 "완성 정의" 절이 비어 있지 않고, "범위 밖" 절에 이번에 하지 않을 것이 적혀 있다.

## C2. 되돌리기 어려운 결정은 사람에게

- **규칙:** 데이터 스키마, 외부 API 계약, 인증 방식, 공개 URL 구조처럼 나중에 바꾸기 비싼 결정은 에이전트가 정하지 않는다. "사람 결정 필요" 로 표시하고 선택지와 각각의 대가를 적는다.
- **이유:** 되돌리기 어려운 결정을 추측으로 정하면, 게이트를 통과한 뒤에야 틀린 것을 알게 된다.
- **적용 조건:** 결정이 다른 시스템·데이터·사용자에게 새어 나갈 때. 파일 안에서 끝나는 결정은 해당하지 않는다.
- **확인 방법:** 설계 문서의 결정 표에서 해당 결정의 상태가 "사람 결정 필요" 이거나, 사람의 답이 기록돼 있다.

## C3. 필요한 만큼만 추상화

- **규칙:** 요구되지 않은 계층·인터페이스·설정 옵션을 만들지 않는다. 구현이 하나뿐이고 바뀔 계획이 없으면 추상화하지 않는다.
- **이유:** 이전 파일럿에서 규칙을 강하게 걸자 단순 과제가 과설계됐다(품질 −2.5).
- **적용 조건:** 항상. 단, 이미 코드베이스에 있는 추상화를 따르는 것은 과설계가 아니다.
- **확인 방법:** 설계 문서의 구성 요소마다 "왜 필요한가" 가 요구사항이나 완성 정의로 이어진다. 이어지지 않으면 뺀다.

## C4. 검증할 수 있어야 한다

- **규칙:** 설계 요소마다 그것이 되었는지 확인하는 방법을 적는다. 가능하면 실행 가능한 명령(테스트)으로 적는다.
- **이유:** 루프는 acceptance 명령으로만 통과를 판정한다. 확인 방법이 없는 설계 요소는 루프에 넣을 수 없다.
- **적용 조건:** 항상. 테스트 환경이 없으면 "테스트 환경 구성" 을 첫 기능으로 둔다.
- **확인 방법:** 설계 문서의 "검증 계획" 에 구성 요소마다 한 줄 이상 있다.

## C5. 기존 관례를 먼저 따른다

- **규칙:** 새 방식을 고르기 전에 이 저장소가 이미 쓰는 방식(폴더 구조, 상태 관리, 데이터 접근, 스타일링)을 찾아 따른다. 바꾸려면 이유를 적는다.
- **이유:** 한 저장소에 같은 일을 하는 방식이 둘이면 이후 모든 변경이 어느 쪽을 따를지 고민하게 된다.
- **적용 조건:** 기존 코드가 있을 때.
- **확인 방법:** 설계 문서의 "현재 상태" 절에 따를 관례가 파일 경로와 함께 적혀 있다.
