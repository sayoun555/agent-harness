# 코드 기준 — 백엔드 (초안)

> 설계 문서가 아니라 **코드**를 볼 때의 기준이다. 루프의 검증자가 이 기준으로 판정한다.
> 이전 프로젝트의 코딩 규칙(§1 클린 코드, §2 OOP, §3 객체지향 설계, §5 파일 분리)을 옮기고, 디자인 패턴과 설정을 더했다.
> 공통 기준 C3(필요한 만큼만)가 이 파일의 모든 기준보다 앞선다. 기준을 지키려고 요구되지 않은 클래스를 만드는 것은 위반이다.
> 이 파일 안에서 부딪히면 번호가 작은 쪽이 이긴다.

## K1. 이름이 의도를 드러낸다 (§1)

- **규칙:** 변수·메서드·클래스 이름만 읽고 무엇을 왜 하는지 알 수 있어야 한다. 약어, `data`·`info`·`temp`·`manager` 같은 뜻 없는 이름을 쓰지 않는다. 불리언은 `is`·`has`·`can` 으로 시작한다.
- **이유:** 이름이 설명하지 못하는 코드는 주석이 필요하고, 주석은 코드와 어긋난다.
- **적용 조건:** 새로 쓰거나 바꾼 코드. 바꾸지 않은 기존 이름을 이번 기능에서 고치지 않는다.
- **확인 방법:** 검증자가 바뀐 이름 중 뜻이 드러나지 않는 것을 지적한다.

## K2. 메서드는 한 가지 일만 한다 (§1)

- **규칙:** 메서드는 한 가지 일만 하고 짧게 유지한다. 들여쓰기는 두 단계를 넘기지 않는다. 깊어지면 조기 반환이나 메서드 추출로 편다. 주석으로 단락을 나눠야 할 정도면 메서드로 나눈다.
- **이유:** 여러 일을 하는 메서드는 이름을 붙일 수 없고, 한 부분을 고치면 다른 부분이 깨진다.
- **적용 조건:** 새로 쓰거나 바꾼 메서드.
- **확인 방법:** 검증자가 들여쓰기 세 단계 이상이거나 여러 일을 하는 메서드를 지적한다.

## K3. 클래스는 변경 이유가 하나다 (§3 SRP, §5)

- **규칙:** 클래스가 바뀌어야 하는 이유는 하나다. 책임이 둘이 되면 역할에 맞는 클래스(Validator, Mapper, Policy 등)로 나눈다. 파일이 길어지거나 public 메서드가 많아지는 것은 그 신호다.
- **이유:** 책임이 섞인 클래스는 한쪽 변경이 다른 쪽을 깨뜨리고 테스트가 커진다.
- **적용 조건:** 새로 쓰거나 크게 바꾼 클래스. 기존의 큰 클래스를 이번 기능과 무관하게 쪼개지 않는다.
- **확인 방법:** check 게이트의 파일 크기·public 메서드 수 경고. 검증자가 책임이 둘 이상인 클래스를 지적한다.

## K4. 객체에 일을 시킨다 (§2 캡슐화)

- **규칙:** 데이터와 그것을 다루는 행위를 한 객체에 둔다. 값을 꺼내서 밖에서 판단하지 말고 객체에 물어본다(Tell, Don't Ask). setter 로 상태를 바꾸지 말고 의미 있는 메서드(`cancel()`, `approve()`)로 바꾼다. getter 는 필요한 것만 둔다.
- **이유:** 밖에서 상태를 꺼내 판단하면 같은 판단이 여러 곳에 복사되고, 객체의 불변식을 아무나 깨뜨린다.
- **적용 조건:** 도메인 객체. DTO·설정 객체·외부 응답처럼 데이터를 나르기만 하는 객체에는 적용하지 않는다.
- **확인 방법:** 검증자가 도메인 객체의 setter 추가, 밖에서 getter 로 꺼내 분기하는 코드를 지적한다.

## K5. 원시 타입을 포장한다 (§2)

- **규칙:** 도메인 의미와 규칙이 있는 값(금액·이메일·좌표·수량)은 원시 타입 대신 값 객체로 포장한다. 검증은 생성 시점에 한 번 한다. Java 21 이면 `record` 와 컴팩트 생성자로 쓴다.
- **이유:** `long price` 는 음수도, 다른 통화도 받는다. 포장하면 잘못된 값이 처음부터 만들어지지 않는다.
- **적용 조건:** 값에 규칙(범위·형식·단위)이 있을 때. 규칙 없는 단순 숫자·문자열까지 포장하지 않는다 (C3).
- **확인 방법:** 구성 요소나 diff 의 값 객체에 생성 시점 검증이 있다. 규칙이 있는 값이 원시 타입으로 여러 메서드를 오가면 검증자가 지적한다.

## K6. 컬렉션에 규칙이 붙으면 일급 컬렉션으로 (§2)

- **규칙:** 컬렉션에 불변식(중복 금지·개수 제한·정렬)이나 그 컬렉션에 대한 연산(합계·필터·검증)이 붙으면, 그 컬렉션 하나만 필드로 가진 클래스로 감싼다. 밖으로는 수정할 수 없는 사본이나 읽기 메서드만 내보낸다.
- **이유:** `List<Order>` 를 여러 서비스가 직접 다루면 같은 합계·검증 로직이 흩어지고, 누군가 리스트를 직접 고쳐 불변식을 깨뜨린다.
- **적용 조건:** 컬렉션에 규칙이나 연산이 있을 때. 그냥 담아서 넘기기만 하는 리스트는 감싸지 않는다 (C3).
- **확인 방법:** 같은 컬렉션 연산이 두 곳 이상에 있거나, 불변식이 있는 컬렉션이 수정 가능한 채로 밖에 노출되면 검증자가 지적한다.

## K7. SOLID — 근거가 있을 때 (§3)

- **규칙:**
  - **OCP:** 같은 종류의 분기가 늘어날 예정이면, 분기를 다형성으로 바꿔 새 종류를 추가할 때 기존 코드를 고치지 않게 한다.
  - **LSP:** 하위 타입은 상위 타입의 약속(사전 조건·반환·예외)을 깨지 않는다. 오버라이드에서 `UnsupportedOperationException` 을 던지면 위반이다.
  - **ISP:** 구현체가 쓰지 않는 메서드를 강요하는 큰 인터페이스는 역할별로 나눈다.
  - **DIP:** 바뀔 수 있는 외부 경계(저장소·외부 API·시계·난수)는 인터페이스로 받는다.
- **이유:** 각 원칙은 특정한 변경 비용을 줄이기 위한 것이다. 그 변경이 오지 않으면 비용만 남는다.
- **적용 조건:** 원칙이 막으려는 변경이 실제로 예정됐거나 이미 두 번 이상 일어났을 때. 구현이 하나뿐이고 바뀔 계획이 없으면 인터페이스를 만들지 않는다 (C3).
- **확인 방법:** 검증자가 근거 없는 인터페이스·추상 계층(과설계)과, 반복되는 분기를 그대로 둔 것(과소 설계)을 둘 다 지적한다.

## K8. 디자인 패턴은 조건이 맞을 때만

- **규칙:** 패턴은 아래 조건이 실제로 있을 때만 쓴다. 조건 없이 "확장성" 을 이유로 쓰지 않는다.

  | 패턴 | 쓰는 조건 | 쓰지 않는 경우 |
  |---|---|---|
  | Strategy | 같은 기준의 분기(`switch`·`if`)가 두 곳 이상에 반복되고, 종류가 늘어날 예정 | 분기가 한 곳뿐이거나 종류가 고정 — 그때는 `sealed` + 패턴 매칭 `switch` |
  | Factory / 정적 팩토리 | 생성 규칙이 복잡하거나, 입력에 따라 다른 구현을 골라야 함 | 생성자 하나로 충분 |
  | Adapter | 외부 API·라이브러리를 도메인 인터페이스에 맞춰야 함 (B2 경계) | 내부 클래스끼리 |
  | Template Method | 여러 구현이 같은 순서를 따르고 일부 단계만 다름 | 구현이 하나 |
  | Decorator / AOP | 핵심 로직에 부가 기능(로깅·캐시·재시도)을 겹쳐야 함 | 부가 기능이 한 곳에만 필요 |
  | Builder | 선택 인자가 많고 조합이 다양함 | 인자가 몇 개뿐 — `record` 생성자로 충분 |
  | Observer / 도메인 이벤트 | 한 변경에 여러 독립 후속 작업이 반응해야 함 | 후속 작업이 하나이고 같은 트랜잭션 |

- **이유:** 패턴은 특정한 변경을 싸게 만드는 대신 간접 계층을 더한다. 조건 없는 패턴은 간접 계층만 남긴다. 이전 파일럿에서 단순 과제에 구조 규칙을 강하게 걸자 품질이 떨어졌다.
- **적용 조건:** 표의 "쓰는 조건" 이 코드나 요구사항으로 확인될 때.
- **확인 방법:** 패턴을 쓴 코드마다 검증자가 조건이 실제로 있는지 본다. 조건이 없으면 과설계로 반려한다.

## K9. 설정은 타입 있는 객체로 한곳에서

- **규칙:**
  - 관련 설정은 `@ConfigurationProperties` 로 묶어 `record` 로 받는다. 여기저기 흩어진 `@Value` 를 쓰지 않는다.
  - `@Validated` 와 제약(`@NotBlank`, `@Positive` 등)으로 **시작할 때** 검증한다. 잘못된 설정으로 뜬 뒤 런타임에 터지게 두지 않는다.
  - 환경별 값은 프로필(`application-{profile}.yml`)로 나누고, 비밀은 `${이름}` 참조만 둔다 (B8).
  - 기능 켜기·끄기는 설정 값과 `@ConditionalOnProperty` 로 한다. 코드의 `if (env == prod)` 로 하지 않는다.
  - 매직 넘버·URL·시간 제한은 이름 있는 상수나 설정으로 뺀다.
- **이유:** 흩어진 설정은 무엇이 필요한지 알 수 없고, 오타가 운영에서야 드러난다.
- **적용 조건:** Spring Boot. 설정 값이 하나뿐인 작은 모듈은 `record` 로 묶지 않아도 된다.
- **확인 방법:** check 게이트의 하드코딩 URL·호스트 경고. 검증자가 새 `@Value`, 시작 시 검증 없는 설정, 코드 안 환경 분기를 지적한다.
