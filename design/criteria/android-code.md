# 코드 기준 — Android · Kotlin (초안)

> 공통 코드 기준(Q1~Q6)이 먼저다. 부딪히면 공통이 이긴다. 이 파일 안에서는 번호가 작은 쪽이 이긴다.
> 저장소가 이미 다른 구조(예: MVI 라이브러리, 다른 DI)를 쓰면 C5(기존 관례)에 따라 그것을 따른다.

## A1. 화면 상태는 하나의 불변 상태로 흐른다

- **규칙:** 화면마다 ViewModel 이 하나의 UI 상태(`data class` 또는 `sealed interface`)를 `StateFlow` 로 내보내고, 화면은 그 상태를 그리기만 한다. 사용자 동작은 ViewModel 의 함수로 올라간다. 화면이 여러 개의 `LiveData`·`MutableState` 를 따로 들고 조합하지 않는다.
- **이유:** 상태가 흩어지면 화면이 불가능한 조합(로딩 중인데 에러 표시)을 그리고, 회전·재생성 때 일부만 복원된다.
- **적용 조건:** 상태가 있는 화면.
- **확인 방법:** ViewModel 이 화면 상태를 하나의 타입으로 내보내는지, `MutableStateFlow` 가 밖으로 노출되지 않는지 검증자가 본다.

## A2. 코루틴은 구조화된 범위 안에서

- **규칙:** 코루틴은 수명이 있는 범위(`viewModelScope`, `lifecycleScope`, 주입받은 애플리케이션 범위)에서 시작한다. `GlobalScope` 와 범위 없는 `CoroutineScope(...)` 를 만들지 않는다. 블로킹 I/O 는 `withContext(Dispatchers.IO)` 로 옮기고, 디스패처는 주입받아 테스트에서 바꿀 수 있게 한다.
- **이유:** 범위 밖 코루틴은 화면이 사라져도 돌며 메모리와 배터리를 쓰고, 취소되지 않아 낡은 결과로 상태를 덮어쓴다.
- **적용 조건:** 코루틴을 시작하는 코드.
- **확인 방법:** `GlobalScope`, 범위 없는 `launch`, 메인 스레드의 블로킹 호출을 검증자가 지적한다.

## A3. 수명주기를 아는 수집

- **규칙:** UI 에서 Flow 는 `repeatOnLifecycle` 이나 `collectAsStateWithLifecycle` 로 모은다. 오래 사는 객체(싱글턴·Repository)가 `Activity`·`View`·`Fragment` 참조를 들지 않는다. Context 가 필요하면 Application Context 를 쓴다.
- **이유:** 수명주기를 모르는 수집은 백그라운드에서도 돌고, Activity 참조를 잡은 싱글턴은 화면 전체를 누수시킨다.
- **적용 조건:** Flow 를 UI 에서 모으거나, 오래 사는 객체가 Context 를 받을 때.
- **확인 방법:** 검증자가 수명주기 없는 `collect`, 오래 사는 객체의 Activity 참조를 지적한다.

## A4. 데이터는 한곳이 주인이다

- **규칙:** 같은 데이터의 주인은 Repository 하나다. 화면·ViewModel 은 복사본을 따로 들고 고치지 않는다. 데이터 계층(네트워크·DB·BLE)은 UI 계층 타입을 모른다.
- **이유:** 주인이 둘이면 둘이 어긋나고, 어느 쪽이 맞는지 판단하는 코드가 생긴다.
- **적용 조건:** 여러 화면이 같은 데이터를 보거나, 데이터가 갱신될 때.
- **확인 방법:** check 게이트의 금지 import 경고(UI ↔ 데이터 계층)와, 같은 데이터를 두 곳에서 고치는 코드를 검증자가 본다.

## A5. 하드웨어와 외부 콜백은 한 경계 안에 가둔다

- **규칙:** BLE·센서·위치처럼 콜백으로 오는 외부 이벤트는 한 어댑터 클래스가 받아 `callbackFlow` 등으로 바꾸고, 그 안에서 스레드를 한 곳에 가둔다(Q3). 연결·스캔·쓰기 같은 절차는 그 어댑터의 상태 기계로 관리한다(Q2). 앱의 다른 곳은 콜백을 직접 받지 않는다.
- **이유:** 콜백은 임의의 스레드에서 임의의 순서로 온다. 여러 곳에서 받으면 잠금이 늘어나고 순서 버그가 생긴다.
- **적용 조건:** 하드웨어·시스템 콜백을 다룰 때.
- **확인 방법:** 콜백 인터페이스 구현이 한 어댑터 밖에 있거나, 어댑터 밖에 잠금이 있으면 검증자가 지적한다.

## A6. 의존성 주입은 한 방식으로

- **규칙:** 의존성은 생성자로 받고, 주입 방식(Hilt, 수동 DI 등)은 저장소 전체에서 하나로 한다. 클래스 안에서 의존성을 직접 `new` 하거나 싱글턴 `object` 로 꺼내 쓰지 않는다(테스트에서 바꿀 수 없게 된다).
- **이유:** 주입 방식이 섞이면 같은 객체가 두 개 생기고, 테스트에서 가짜로 바꿀 수 없다.
- **적용 조건:** 다른 객체에 의존하는 클래스.
- **확인 방법:** 검증자가 생성자 밖에서 의존성을 만들거나 꺼내는 코드를 지적한다.
