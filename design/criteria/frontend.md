# 설계 기준 — 프론트엔드 (초안)

> 초안이다. 프로젝트 소유자가 우선순위와 적용 조건을 고쳐 확정한다.
> 공통 기준(C1~C5)이 먼저다. 부딪히면 공통이 이긴다. 프론트엔드 기준끼리는 번호가 작은 쪽이 이긴다.

## F1. 데이터와 표현을 분리한다

- **규칙:** 컴포넌트 안에 하드코딩된 데이터(배열, 객체, 문자열 목록)를 데이터 계층으로 옮긴다. 컴포넌트는 데이터를 받아 그리기만 한다. Next.js App Router 라면 데이터는 서버 컴포넌트나 서버 함수에서 가져온다.
- **이유:** 데이터가 컴포넌트에 박혀 있으면 실제 데이터로 바꿀 때 화면 코드를 전부 고쳐야 한다.
- **적용 조건:** 데이터가 바뀌거나 외부에서 올 예정일 때. 절대 안 바뀌는 상수(메뉴 이름 몇 개 등)는 상수 파일로 빼는 것까지만 한다.
- **확인 방법:** 컴포넌트 파일에 데이터 리터럴이 남아 있지 않다. 데이터 계층을 가짜 데이터로 바꿔 끼운 테스트가 통과한다.

## F2. 상태를 나눠서 다룬다

- **규칙:** 서버에서 오는 데이터(서버 상태)와 화면에서만 쓰는 상태(열림·선택·입력값)를 구분한다. 화면 상태는 가장 가까운 컴포넌트의 상태로 둔다. 서버 상태는 환경에 따라 가져오는 곳이 다르다.
  - **Next.js App Router:** 서버 컴포넌트나 서버 함수에서 가져온다. 클라이언트에서 다시 가져와야 하는 경우만 데이터 페칭 도구를 쓴다.
  - **클라이언트 React 앱(Vite 등):** API 호출은 커스텀 훅으로 분리하고, 훅 안에서 데이터 페칭 도구(TanStack Query 등)를 쓴다. 컴포넌트가 직접 API 를 부르지 않는다.
  - 어느 쪽이든 useEffect 로 직접 데이터를 가져오지 않는다.
- **이유:** 둘을 섞으면 캐시·재시도·취소·에러 처리가 빠지고, 같은 데이터가 여러 곳에 복사된다. 호출이 컴포넌트에 흩어지면 API 가 바뀔 때 화면을 전부 고쳐야 한다.
- **적용 조건:** 서버 데이터가 있을 때. 환경은 "현재 상태" 절에서 확인한 것을 따른다 (C5).
- **확인 방법:** 설계 문서의 상태 표에 상태마다 종류(서버·화면)와 위치가 적혀 있다. 클라이언트 앱이면 컴포넌트 파일에 API 호출이 없고, 훅을 가짜로 바꿔 끼운 테스트가 통과한다.

## F3. 모든 상태를 그린다

- **규칙:** 데이터를 보여 주는 화면마다 로딩, 에러, 빈 상태를 설계한다. 성공 상태만 있는 화면은 완성이 아니다.
- **이유:** 하드코딩된 화면은 항상 데이터가 있어서 이 세 상태가 빠져 있다. 실제 데이터로 바꾸는 순간 드러난다.
- **적용 조건:** 비동기 데이터를 보여 주는 화면.
- **확인 방법:** 화면마다 세 상태를 확인하는 테스트가 있다. 가짜 데이터 계층이 지연·실패·빈 결과를 돌려주게 해서 확인한다.

## F4. 디자인 시스템을 따른다

- **규칙:** 하드코딩된 색·간격·글자 크기를 디자인 토큰으로 바꾼다. 이미 있는 컴포넌트가 있으면 새로 만들지 않고 재사용하거나 variant 로 넓힌다.
- **이유:** 하드코딩된 값은 다크 모드·브랜드 변경·일관성을 깨뜨린다. 같은 역할의 컴포넌트가 둘이면 계속 갈라진다.
- **적용 조건:** 저장소에 토큰이나 컴포넌트 라이브러리가 있을 때. 없으면 C3 가 이긴다. 토큰 체계를 새로 만들지 말고, 반복되는 값만 상수로 모은다.
- **확인 방법:** 바뀐 컴포넌트에 임의 값(예: Tailwind `text-[#333]`)이 없다. 설계 문서의 구성 요소 표에 재사용한 기존 컴포넌트가 적혀 있다.

## F5. 접근성과 성능

- **규칙:** 클릭되는 것은 button·a 를 쓰고, 이미지에 alt, 입력에 label 을 단다. 무거운 렌더는 서버 컴포넌트로 두고 'use client' 경계를 최소로 한다.
- **이유:** 에이전트는 디자인에 접근성 정보가 없으면 기본으로 빠뜨린다.
- **적용 조건:** 사용자에게 보이는 화면.
- **확인 방법:** 접근성 린트(jsx-a11y 등)가 있으면 통과한다. 없으면 핵심 흐름을 키보드로만 조작하는 테스트가 통과한다.
