# 설계 기준 — 백엔드 (초안)

> 이전 프로젝트(Java 21 · Spring Boot · 멀티 모듈 · DDD)의 코딩 규칙에서 **설계 단계에 쓰는 것**만 옮겼다. 괄호 안 § 는 원래 규칙 번호다.
> 네이밍·메서드 크기·파일 분리·트러블슈팅 기록 형식은 설계가 아니라 코드를 볼 때의 규칙이라 여기 두지 않는다. 그것은 프로젝트의 AGENTS.md 와 검증자가 맡는다.
> 공통 기준(C1~C5)이 먼저다. 부딪히면 공통이 이긴다. 백엔드 기준끼리는 번호가 작은 쪽이 이긴다.
> 프로젝트에 설계 문서(designDocsDir)가 있으면 그것이 "현재 상태" 의 첫 출처다. 읽지 않고 다르게 설계하지 않는다. 읽고 나서 더 나은 방법이 있으면 바꾸되, 결정 표에 근거를 적는다 (§0, C5).

## B1. 정석적인 방법을 먼저 찾는다 (§4)

- **규칙:** 프레임워크·라이브러리의 공식 권장 방식을 먼저 찾고 그것으로 설계한다. 임시방편, 우회, 빌드 스크립트 꼼수는 설계에 넣지 않는다.
- **이유:** 우회 해법은 동작해도 기술 부채가 되고, 다음 사람이 이유를 모른다.
- **적용 조건:** 항상.
- **확인 방법:** 설계 결정 표에서 프레임워크 기능을 쓰는 결정의 근거에 공식 문서나 기존 코드 관례가 적혀 있다.

## B2. 의존성 방향을 지킨다 (§8, §10)

- **규칙:** `api → application → domain ← infrastructure`. 도메인은 다른 레이어와 인프라(웹·DB 드라이버·메시지 브로커)에 의존하지 않는다. 저장소 인터페이스는 도메인에, 구현은 인프라에 둔다. 멀티 모듈이면 핵심 도메인 모듈은 다른 모듈에 의존하지 않는다.
- **이유:** 도메인이 인프라에 묶이면 저장소나 외부 연동을 바꿀 때 비즈니스 로직까지 흔들린다.
- **적용 조건:** 레이어나 모듈이 나뉜 코드베이스. 작은 단일 모듈 서비스에 레이어를 새로 만들지 않는다 (C3).
- **확인 방법:** 구성 요소 표에 요소마다 레이어가 적혀 있다. 금지된 import 를 잡는 린트나 아키텍처 테스트가 통과한다.

## B3. 비즈니스 규칙은 도메인이 가진다 (§8)

- **규칙:** 판단·계산·상태 변경은 Entity 와 VO 에 둔다. Application Service 는 순서를 조율할 뿐 규칙을 갖지 않는다. Domain Service 는 여러 Aggregate 에 걸친 규칙에만 쓴다. Controller 는 입력 검증과 응답 변환만 한다.
- **이유:** 규칙이 서비스에 흩어지면 같은 규칙이 여러 곳에 복사되고, 도메인 단위 테스트를 할 수 없다.
- **적용 조건:** 비즈니스 규칙이 있는 도메인. 규칙 없는 단순 조회·저장에 억지로 도메인 메서드를 만들지 않는다 (C3).
- **확인 방법:** 구성 요소 표에서 규칙을 가진 요소가 도메인 레이어에 있다. 그 규칙마다 도메인 단위 테스트가 검증 계획에 있다.

## B4. 쓰기마다 일관성 등급을 정한다 (§9)

- **규칙:** 데이터를 쓰는 흐름마다 등급을 결정 표에 적는다.
  - **강한 일관성**(돈·사용자 데이터): 트랜잭션. 동시에 고쳐질 수 있으면 낙관적 락.
  - **최종 일관성**: 이벤트나 메시지로 나중에 맞춘다.
  - **불필요**(캐시·로그): 실패해도 흐름을 멈추지 않는다.
- **규칙:** 외부 API(결제·HTTP)는 트랜잭션 안에서 부르지 않는다. 외부 호출 → 성공하면 짧은 트랜잭션으로 저장 → 실패하면 보상 트랜잭션. 읽기 전용 조회는 읽기 전용 트랜잭션.
- **이유:** 트랜잭션 안의 외부 호출은 커넥션을 붙잡고 롤백할 수 없다. 등급 없이 쓰면 캐시 실패가 결제를 멈추거나, 결제가 최종 일관성으로 처리된다.
- **적용 조건:** 데이터를 쓰는 흐름.
- **확인 방법:** 설계 결정 표에 쓰기 흐름마다 등급이 있다. 외부 호출 실패와 보상을 확인하는 테스트가 검증 계획에 있다.

## B5. 메시지 브로커는 근거가 있을 때만 (§9, §12)

- **규칙:** 기본은 받은 자리에서 바로 저장한다. 메시지 브로커는 다음 중 하나가 **측정으로** 확인될 때만 쓴다: 직접 저장이 못 따라가는 처리량, 서로 독립적으로 소비해야 하는 여러 소비자, 수신과 처리를 떼어야 하는 역압.
- **규칙:** 쓰기로 했으면: 순서가 필요한 단위로 파티션 키를 정하고, 재시도 뒤 실패는 DLT 로 보내고, 처리가 끝난 뒤에 수동으로 커밋한다. 브로커가 없어도 나머지 기능은 돌아가야 한다.
- **이유:** 이전 프로젝트는 모든 수집에 브로커를 썼다가, 대부분이 초당 1건도 안 되는 것을 측정하고 한 경로만 남겼다. 나머지는 구성 요소·장애 지점만 늘렸다.
- **적용 조건:** 비동기 처리를 설계할 때.
- **확인 방법:** 브로커를 쓰는 결정의 근거에 처리량이나 소비자 구조의 수치가 있다. 없으면 직접 저장으로 설계한다.

## B6. API 는 계약이고, 호출하는 쪽까지 연결돼야 완성이다 (§13, §15)

- **규칙:** 메서드는 REST 의미를 따른다. 페이지 응답과 에러 응답은 저장소 전체에서 한 형식이다. URL 에 버전을 넣지 않고 하위 호환을 지킨다. 응답 DTO 와 호출하는 쪽의 타입은 한 번에 같이 바꾼다.
- **규칙:** API 는 호출하는 코드(프론트엔드·다른 서비스)까지 연결돼야 완성이다. 백엔드만 되는 것은 미완성이다.
- **이유:** 한쪽만 바뀐 계약은 컴파일을 통과하고 런타임에 깨진다.
- **적용 조건:** 외부에 노출되는 API. 새 공개 엔드포인트와 응답 형식은 되돌리기 어렵다 — C2 에 따라 사람이 정한다.
- **확인 방법:** 검증 계획에 계약 테스트(요청·응답 예시 대조)가 있다. 호출하는 쪽이 이 저장소에 있으면 그쪽 테스트도 있다.

## B7. 데이터 접근을 설계한다 (§11)

- **규칙:** 목록 조회는 페이지네이션한다. 연관 데이터는 한 번에 가져와 N+1 을 막는다. 캐시는 모든 키에 만료 시간을 두고, 캐시 실패는 로그만 남기고 흐름을 멈추지 않는다. 저장소는 접근 패턴(공간 검색·그래프 탐색·전문 검색 등)에 맞춰 고른다.
- **이유:** 이 문제들은 데이터가 적을 때는 안 보이다가 운영에서 한꺼번에 터진다.
- **적용 조건:** 영속 데이터를 다룰 때. 저장소를 새로 들이는 결정은 되돌리기 어렵다 — C2.
- **확인 방법:** 검증 계획에 목록 API 의 페이지 파라미터 테스트와, 연관 조회의 쿼리 수를 확인하는 테스트가 있다.

## B8. 비밀은 코드와 설정 파일에 두지 않는다 (§6)

- **규칙:** API 키·DB 비밀번호·토큰은 환경 변수나 비밀 관리 도구로 주입한다. 설정 파일에는 `${이름:기본값}` 형태의 참조만 둔다. `.env` 는 커밋하지 않는다.
- **이유:** 한 번 커밋된 비밀은 기록에서 지우기 어렵다.
- **적용 조건:** 항상.
- **확인 방법:** 하네스의 check 게이트(시크릿)가 통과한다. 설계 문서의 구성 요소에 필요한 환경 변수 이름이 적혀 있다.

## B9. 모던 Java 로 표현한다 (§2)

- **규칙:** 불변 값은 `record`(검증은 컴팩트 생성자). 닫힌 종류(등급·상태·결과)는 `sealed interface` + record, 분기는 패턴 매칭 `switch`. 원시 타입 포장과 일급 컬렉션은 도메인 의미가 있을 때 쓴다.
- **이유:** 수동 `equals/hashCode/getter` 는 장황하기만 하고 틀리기 쉽다. 닫힌 계층은 빠진 분기를 컴파일러가 잡는다.
- **적용 조건:** Java 21 이상. 행위와 엄격한 캡슐화가 필요한 값은 일반 클래스로 둔다.
- **확인 방법:** 구성 요소 표에서 값 객체와 닫힌 계층의 표현 방식이 적혀 있다.
